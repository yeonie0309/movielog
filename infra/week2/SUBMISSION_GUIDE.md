## 1. 맨 위 ‘📸 잠깐! 스터디 인증샷’

실제 팀 스터디 사진을 직접 첨부한다. API·Grafana·테스트 화면은 스터디 참석 사진을 대신하지 않는다. 학습 전후 스터디를 실제로 했다면 날짜와 팀명을 함께 적는다.

## 2. 본문 1~7

본문 안내를 따라 구현·실행했다. 본문 설명을 지우거나 예제 숫자를 본인 수치로 착각하지 않는다. logs/trace는 개념을 읽는 범위이며 본문에서도 이번주 별도 설치를 제외한다.

기술 증빙 사진은 아래 ‘미션 기록’에 모으고, 필수 미션의 SLO·표·알림 사진은 해당 필수 위치에도 넣는다. 작성 중 토큰 원문·비밀번호·Authorization 헤더를 붙이지 않는다.

## 3. ‘🎯 핵심 키워드’

기존 키워드 토글 안의 안내 문구를 아래 정의로 채운다. 문서의 설명을 이해한 뒤 본인 표현을 조정해도 된다.

**모니터링과 관측 가능성**
모니터링은 미리 정한 지표와 기준으로 시스템의 상태·이상을 확인하는 활동이다. 관측 가능성은 메트릭·로그·추적 등 외부 출력을 통해 내부 상태와 원인을 추론할 수 있는 성질이다. CPU 상승을 발견하는 것과 어떤 요청·DB 작업 때문에 느려졌는지 설명하는 것은 서로 다른 단계다.

**Grafana**
Prometheus 등 데이터 소스를 조회하고 지표를 대시보드로 시각화하며, 조건에 따라 알림을 보내는 도구다. Grafana 화면 자체가 앱 지표를 생성하는 것은 아니다. 앱 계측 → Alloy 수집·전송 → Prometheus 저장 → Grafana 조회 흐름을 구분한다.

**Grafana Alloy**
메트릭 등 관측 데이터를 수집·처리·전송하는 수집기다. Fleet Management의 원격 설정을 받아 여러 인스턴스에 같은 파이프라인을 적용할 수 있다. 인스턴스의 정상 실행과 메트릭 전송 성공은 별도로 확인해야 한다.

**Prometheus와 시계열**
메트릭 이름과 라벨 조합으로 식별하는 시계열에 시간별 숫자 표본을 저장하고 PromQL로 조회하는 시스템이다. 같은 지표라도 instance 라벨이 다르면 다른 시계열이다. 두 앱의 localhost 주소가 같아도 호스트별 instance 라벨을 붙여 서로 다른 앱을 구분한다.

**Counter · Gauge · Histogram**
Counter는 재시작 전까지 누적 증가하는 값으로 요청 건수 등에 사용한다. Gauge는 현재 연결 수·메모리 사용량처럼 증감하는 값이다. Histogram은 응답 시간을 구간별 누적 개수와 합계로 기록한다. 요청 Counter의 누적 수 자체와 초당 요청량을 혼동하지 않는다.

**rate와 PromQL 집계**
rate는 일정 시간 창에서 Counter의 초당 평균 증가율을 계산한다. sum은 여러 시계열을 합치고 avg는 평균, max는 최댓값을 구한다. 같은 RDS를 두 수집기가 관측한 연결 수는 합산하면 이중 집계가 되므로 max로 조회한다. 요청량의1분 창과 지연의5분 창은 서로 다른 평활화 결과다.

**histogram_quantile과 p95**
histogram_quantile은 Histogram bucket의 누적 분포에서 분위수를 추정한다. p95는 관측된 지연의 약95%가 그 값 이하라는 뜻이다. 전체 평균과 다르며, 인스턴스별 p95를 평균내도 전체 p95가 되지 않는다. 전체 bucket을 le 기준으로 집계한 뒤 분위수를 계산한다. 5초 timeout으로 응답이 없던 요청은 도구의 지연 표본에서 빠지므로 실패 수를 함께 봐야 한다.

**카디널리티(Cardinality)**
메트릭에서 서로 다른 라벨 조합으로 생성되는 시계열의 수다. 사용자 ID·이메일·원시 URL을 라벨에 넣으면 시계열이 과도하게 늘고 민감 정보도 노출될 수 있다. 경로는 `/members/:id` 같은 템플릿을 사용하고 임의404 경로는 `/unmatched`로 고정한다.

**SLI · SLO**
SLI는 성공 비율·응답 지연처럼 서비스 수준을 측정하는 지표다. SLO는 그 지표가 충족해야 할 목표다. ‘p95 ≤1초, 201 비율 ≥99%’는 목표이며, 실제 달성 여부는 부하 조건과 관측 창을 함께 제시해야 판단할 수 있다. SLO를 문서에 적었다는 사실만으로 달성한 것은 아니다.

**처리량 · 지연 · 미전송**
처리량은 일정 시간에 실제 완료한 요청 수이고 지연은 요청을 완료하기까지 걸린 시간이다. 목표 RPS와 실제 처리량은 다를 수 있다. dropped는 측정기가 예정한 요청을 보내지 못한 수로, 서버의 HTTP 실패와 분리해 기록한다. 800 RPS 단계에서는 전송된 요청이 모두201이어도 미전송4,676건과 p95 1.911초 때문에 정상 처리라고 단순화할 수 없다.

**threads_connected · threads_running**
threads_connected는 현재 열려 있는 MySQL 연결 수이고 threads_running은 잠자고 있지 않은 실행 스레드 수다. 연결 수가 많다는 사실만으로 모두 쿼리를 실행 중이라는 뜻은 아니다. 본 실험의 표는 관측기 연결을 포함한 동일 DB의 최댓값이다.

**알림의 평가 간격과 Pending period**
평가 간격은 조건을 얼마나 자주 계산할지, Pending period는 임계값 초과가 얼마나 지속되어야 Firing으로 전환할지 정한다. 실습 규칙은20초마다 p95를 계산하고 1초 초과가1분 지속될 때 본인 이메일로 보낸다. 규칙 저장 화면과 실제 알림 수신 화면을 구분한다.

참고: [Prometheus 지표 타입](https://prometheus.io/docs/concepts/metric_types/), [PromQL 함수](https://prometheus.io/docs/prometheus/latest/querying/functions/), [Histogram 설명](https://prometheus.io/docs/practices/histograms/), [Alloy 문서](https://grafana.com/docs/alloy/latest/).

## 4. ‘📢 학습 후기’

아래는 실제 진행 결과에 근거한 초안이다. 본인이 이해한 내용과 다르면 수정하고 제출한다.

> 평균 지연이나 HTTP 오류 수만으로 서비스 상태를 판단할 수 없다는 점을 확인했다. 최종800 RPS 단계에서 응답한 요청은 모두201이었지만 p95는1.911초였고 측정기가 보내지 못한 요청도4,676건이었다. 성공 응답만 보고 안정적이라고 판단하면 사용자 대기와 실제 부하 누락을 놓치게 된다.
>
> 처음에는 SSM 연결 경로에서600 RPS 이후 timeout이 늘었다. 하지만 앱에 직접 상태 확인을 요청하면 약2~3ms로 응답했고, 내부망의 별도 부하 서버로 다시 측정하자 결과가 달라졌다. 부하 도구와 연결 경로도 실험 조건에 포함해야 한다는 점을 배웠다.
>
> PromQL의 시간 창과 집계 방식도 확인했다. 40초 부하의 원시 p95와 Grafana의5분 Histogram p95는 계산 창과 추정 방식이 달라 정확히 같은 값이 아니다. 같은 RDS를 두 번 수집한 연결 수를 sum으로 합치지 않고 max로 조회했다.
>
> 현재 실험에서는 목표800 RPS에서 처리량 증가폭이 줄고 지연 SLO를 위반했다. 다만 앱 단독의 절대 한계를 증명한 것은 아니므로, 추가로 원인을 좁히려면 측정기의 발사율과 앱 프로세스 CPU·DB 지표를 함께 확인하고 반복 측정해야 한다.

## 7. ‘⚡ 트러블 슈팅’ → ‘⚡ 이슈 No.1’

**이슈**
Mac에서 SSM 터널을 통해 부하를 보낼 때600 RPS 이후 timeout과 network 실패가 늘고, 부하 후에는 터널의 `/health` 요청도 응답하지 않았다.

**문제**
부하 발생기·터널·앱이 한 측정 경로에 포함되어 있어 연결 경로의 한계를 앱 서버 장애와 혼동할 수 있었다. 앱 서버 안에서 직접 요청한 `/health`는 약2~3ms로 정상 응답했다. 실패 수만 보고 서버의 처리 한계를600 RPS로 확정할 근거가 부족했다.

**해결**
터널을 종료하고 동일 VPC의 별도 EC2에서 공식 createRun/createProber 엔진으로200/400/600/800 RPS를 다시 측정했다. 단계마다 새 회원/JWT를 사용하고 CPU·DB 상태도 동시에 기록했다. 최종800 단계에서 처리량 증가 둔화와 p95 1.911초를 관측했다. 터널 실험·예비 실험·최종 실험을 별도 파일로 보존하고 미전송도 HTTP 실패와 분리했다.

## 8. 필요하면 추가 ‘⚡ 이슈 No.2’

**이슈:** 실습 자원을 삭제할 때 보안 그룹 삭제가 DependencyViolation으로 실패했다.

**문제:** 내부 ALB는 앱 보안 그룹에서만80번 접근을 허용하고, 앱은 ALB 보안 그룹에서만3000번 접근을 허용해 두 그룹이 서로를 참조했다. 서버·ALB가 삭제된 뒤에도 그룹 사이 규칙의 참조가 남아 있었다.

**해결:** 정리 요청이 확인된 실습 그룹의 역방향 참조만 해제하고 삭제를 재실행했다. EC2/RDS/ALB/EBS0개와 실습 전용 역할·보안 그룹·SSM 설정·이미지 저장소 제거를 별도 조회로 확인했다.

**참고레퍼런스:** https://docs.aws.amazon.com/vpc/latest/userguide/deleting-security-groups.html
